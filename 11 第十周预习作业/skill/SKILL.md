根据当前实验题目、代码和实际证据，协助完成实验分析与博客报告，并将可复用的方法逐步沉淀到本技能。

开展课程实验或更新本技能前，先读[课程实验学习与演进记录](references/课程实验学习与演进记录.md)，了解已形成的方法和尚待验证的事项。

## 工作原则

- 区分用户当前请求与课程材料描述的作业要求。课程材料中的发布、登录或提交要求不自动授权代用户操作外部平台。
- 只将源码、实际终端输出和截图能支持的内容写成实验事实；把原理推断和未验证事项明确区分。
- 将运行日志对应到实际代码路径。单个回调或打印日志只能证明该路径被调用，不能单独证明更高层机制（如任务轮转）已经实现。
- 不编造运行结果、截图、姓名、课程链接或博客 URL；缺少证据时标明待补项。
- 按当前实验选择方法，不把旧实验命令或分析模板机械套用到新版本。
- 若课程云机按实验重置环境，每次都把它视为全新状态：以前实验中的 MenuOS 命令、二进制、补丁、rootfs 和截图只能作为参考，不能假设仍在当前镜像中。先检查当前文件、`help` 输出、源码和构建入口，再决定是否需要重建；优先设计不依赖旧实验产物的验证路径。

## 实验工作流程

### 1. 梳理题目和证据

提取实验目标、指定环境、代码/命令、需要分析的机制、截图要求、署名与来源格式、交付方式。标明现有材料分别能证明什么，以及下一步最有价值的观察点。

### 2. 复现、调试并留存证据

依据已有材料决定是否需要重跑。记录实际命令和关键输出；截图应能读清文件/函数、命令或调试状态。避免重复采集已经清楚的证据。

整理截图时先逐张检查内容，再按证据顺序用语义化文件名重命名；连续滚屏的上下页若各自包含独有代码或输出，应保留并在报告中连续引用。只删除确认重复或与实验无关的图，无法确认时先保留。反汇编等长输出完整保存为文本，再从关键指令附近截取短图，不要求把整个终端输出塞入截图。

#### Linux 内核源码、补丁、编译与 QEMU

遇到 Linux 内核源码实验时：

- 核对内核版本、补丁路径和源码根目录；按课程指示应用补丁。若有条件，检查补丁涉及的文件和构建入口。像 `mykernel` 这样的教学目录通常是被补丁接入内核构建的实验代码，不应默认视为独立内核。
- 按当前实验给出的配置和编译命令操作。只有看到镜像构建完成等成功结果，才记录为编译成功。仅在课程明确要求时清理旧目录，并确认清理路径。
- 从含有目标镜像的目录启动 QEMU，避免相对路径错误。把启动日志、定时器回调日志和任务输出分开记录，并回到源码核对对应关系。
- 若实验只要求指定文件的源码截图，按要求展示完整相关函数；是否实现了题目中的机制，仍按源码和运行证据判断。

实验命令示例（路径和版本必须以当前课程材料为准）：

```bash
cd ~/LinuxKernel/linux-3.9.4
patch -p1 < ../mykernel_for_linux3.9.4sc.patch
make allnoconfig
make
qemu -kernel arch/x86/boot/bzImage
```

#### 使用 GDB 跟踪内核启动

当实验要求跟踪 `start_kernel` 到 init 启动时：

- 确认 `vmlinux` 与 QEMU 启动的 `bzImage` 来自同一版本和构建。按课程要求用 QEMU GDB stub（常见为 `-s -S`），在另一终端加载符号、连接远程目标、设置断点并继续运行。
- 从 `start_kernel` 开始，用 `bt`、`list`、`info args` 等命令保存调用栈和源码上下文；选择关键断点追踪到 `rest_init`、init 内核线程和执行用户态 init 的位置。函数名和调用结构依内核版本核对。
- 分阶段说明 `start_kernel` 的初始化职责，避免把单步遍历每一行当作分析。解释 PID 0 idle 和 PID 1 时，依据该版本启动任务和 `rest_init` 的创建顺序。
- 命中 `run_init_process` 或等效位置表示内核准备执行 init；用户态提示符是后续运行证据。若它们来自不同运行，报告中明确区分。GDB 无法解析 `current` 等内核宏不等于内核启动失败，应结合源码和调用栈分析。

#### 使用库函数 API 与内嵌汇编调用系统调用

当实验要求以库函数和 C 内嵌汇编调用同一个系统调用时：

- 先确认目标架构、位数与 ABI，再查对应版本/架构的系统调用表。系统调用号和参数寄存器不是跨架构通用值；例如 32 位 x86 的 write 是 4，参数依次经 ebx、ecx、edx，x86-64 约定不同。
- 优先选参数简单、输出容易验证的调用（例如 write），并按要求避开禁选项。实验代码应让 API 与内嵌汇编使用同一个调用、相同参数或等价数据，并比较返回值。
- 内嵌汇编要说明输入、输出和 clobber 约束。对于 32 位 x86 int 0x80，检查 eax 中的调用号、ebx/ecx/edx 中的参数、执行入口指令及 eax 返回值；不能把 C 函数调用约定误当成系统调用 ABI。
- 区分 libc API 与直接系统调用的错误语义：libc 通常把内核负错误码转换为 -1 并设置 errno；直接入口通常把负错误码原样返回，调用者需按代码处理。不要仅凭 write@plt 就断言 libc 内部使用了 int 0x80。
- 编译选项需兼容课程镜像中的编译器。若旧版 GCC 不认识 -no-pie，可依据报错改用兼容选项（如 -fno-pie），再用 file 核对目标 ELF 位数。主机 uname -m 与目标程序位数可能不同。
- 用 objdump 等工具观察反汇编时，截图至少要包含 syscall 号与参数寄存器准备、入口指令和返回值处理；若分屏，保证图片连续且标注前后关系。strace 等辅助工具不可用时，记录环境限制即可，不把它当作实验失败，也不编造跟踪证据。
- 博客把代码约束、反汇编、运行输出和 ABI 资料互相印证；明确哪些是截图直接证明的事实，哪些是基于 ABI 的机制解释。库函数路径和手写入口路径要分开说明。
#### 跟踪 32 位 system_call 到 iret

当实验要求分析 Linux 3.18 x86-32 系统调用入口与返回路径时：

- 使用与 QEMU 启动镜像同一构建的 vmlinux；先在具体内核处理函数（例如 sys_write/SyS_write）设断点，以 GDB 命中、info args 和源码位置作为动态证据。
- 检查调用栈和参数，区分用户态通过 int 0x80 进入的系统调用与内核自身直接调用同一处理函数。initramfs 解包阶段出现 xwrite 等内核调用帧时，不要把它误作用户态系统调用；结合 fd、调用上下文和用户操作判断。
- GDB 在普通 C 内核函数处命中，不等于已单步跟踪入口汇编。若 32 位 entry_32.S 无法从内核栈展开至用户态，记录调试器的限制，并按实际源码分析 system_call、sys_call_table 分派、syscall_exit_work、work_pending、restore_all 与中断返回，不编造动态观测。
- 流程分析要分清 CPU 在特权级转换时建立的返回帧与 SAVE_ALL 等软件保存的通用寄存器现场；解释返回值如何保存到 pt_regs，再由恢复路径带回用户态。
- 说明调度是返回前的条件性时机：work_pending 检查 need_resched 后才可能调用 schedule；不要写成每次系统调用都会切换进程。若发生切换，当前任务的内核栈保留其退出路径，待它之后重新运行再继续返回。
- 流程图和说明以本次内核源码的实际标签、宏和条件分支为准；若 INTERRUPT_RETURN 是返回宏，核对其对应的 iret 语义，并注明 GDB 截图证明的是哪个阶段。
#### 跟踪 Linux 创建新进程

当实验要求分析 `fork`/`sys_clone` 如何创建任务时：

- 先把课程云机视为可能重置的独立环境；用当前 `MenuOS help`、源码和 Makefile 确认正在运行的版本，不把之前实验的 fork 命令或二进制当成本次已存在。若本次确实要求从 MenuOS 发起 fork 且命令不存在，再检查菜单源码、init 构建与 rootfs 打包路径，添加最小测试并在同一当前环境重新构建；若 fork 只用于可选调度触发，则优先选不依赖它的 GDB/内核调度场景。
- 使用同一 Linux 3.18.x 构建的 `vmlinux`/`bzImage`，按实际符号跟踪 `sys_clone`、`do_fork`、`copy_process`、`dup_task_struct`、`copy_thread`、`wake_up_new_task` 和 `ret_from_fork`。旧内核或优化构建下 `bt` 可能无法跨系统调用汇编入口展开；结合 `info args`、断点位置和对应源码，不把不完整栈回溯等同于实验失败。
- 解释 `task_struct` 时区分基础结构复制与资源复制/共享：结合 clone 标志检查 `copy_mm`、`copy_files`、`copy_fs`、`copy_sighand` 等具体路径；普通 fork 并不意味着所有用户页立即完整复制。
- 对 x86 32 位 Linux 3.18.6，`copy_thread` 使用 `task_pt_regs(p)` 准备子任务栈顶寄存器现场，复制父任务现场、把子任务 `ax` 设为 0，并设置 `thread.sp` 与 `thread.ip=ret_from_fork`；`ret_from_fork` 执行 `schedule_tail` 后进入系统调用退出路径。父路径返回子 PID，子路径返回 0。
- 取值必须对应断点执行阶段。该版本 `copy_process` 在 `copy_thread` 之后才分配并写入新 PID，因此 `copy_thread` 入口处看到复制来的父 PID/comm 可以是预期的中间状态；在执行结构字段赋值前读取 `thread.sp`/`thread.ip` 也不是最终子上下文。先用 `list` 对齐当前源码行，再单步越过赋值并重新检查；无法动态确认时明确写为源码分析，不把入口时数字当最终值。
- 用 MenuOS 的父子输出验证 PID 与 fork 返回值，用 `wake_up_new_task`/`ret_from_fork` 断点验证内核路径。两类证据分别证明用户可见结果和内核执行过程，不互相替代。
#### 跟踪 execve、ELF 装载与程序启动

当实验要求分析 `exec*`、ELF 或 `sys_execve` 时：

- 先核对目标 ELF 的位数、架构、入口地址、`PT_INTERP` 和动态依赖。可组合使用 `file`、`readelf -h/-l/-d`、`ldd`；`ldd` 展示的是当前环境解析结果，不能替代 ELF 本身的 `PT_INTERP`/`DT_NEEDED` 证据。记录课程镜像与主机架构差异。
- 分开验证装载时动态链接与运行时动态链接：前者通常在动态节含 `DT_NEEDED`，后者由 `dlopen`/`dlsym` 在程序运行中触发；它们不是 `execve` 本身的两种实现方式。
- 用简短 `execv(path, argv)` 驱动程序验证新映像及 argv；在 MenuOS 中如需父进程继续运行，由子进程执行 `execv`、父进程 `wait`。成功 `execve` 替换当前进程映像，不返回旧程序调用点；只有失败才沿旧映像返回错误。对菜单输入解析需处理 `fgets` 留下的换行符。
- 使用与 QEMU 镜像同一构建的 `vmlinux`，设置 `sys_execve`、`load_elf_binary`、`start_thread` 断点，结合 `bt`、`info args`、`list` 追踪。调用栈若在 syscall/汇编边界停止展开，报告具体边界；后续 C 调用链仍可作为对应路径的观测，不要声称完整展开用户态栈。
- 对照 ELF `e_entry` 与 `start_thread` 的 `new_ip`：没有 `PT_INTERP` 时通常直接进入应用入口；存在解释器时先进入 `PT_INTERP` 指定动态链接器，链接器完成依赖映射与重定位后再转到应用入口。动态入口地址是映射地址，可能受 ASLR 及装载布局影响，不能假设运行间固定。
- 将 `new_sp` 报告为栈指针观测值。初始栈一般承载 `argc`、`argv` 指针数组、`envp` 数组、auxv 及字符串；除非 GDB/内存检查实际读取栈内容，否则将布局标成 ABI/源码机制分析，不声称截图直接证明了每一项。
- 在 MenuOS initramfs 运行动态 ELF 时，逐项检查解释器和共享库依赖，将需要的文件按目标绝对路径组织进 rootfs，再用 `cpio -it` 检查归档。`linux-gate.so.1`/VDSO 是内核提供的映射，不要把它当普通共享库复制进 initramfs。避免让构建目标意外启动另一个普通 QEMU；必要时分开编译、打包和调试启动。
- 博客中分别标记实际截图、源码推理和 ABI 约定；把 `execve` 不返回、静态/动态入口差异、初始用户栈和用户程序输出组成可核对的证据链。
#### 预研：跟踪 Linux 进程调度时机与上下文切换

当实验要求搜索 `schedule()` 调用点、用 GDB 跟踪一次调度并分析 `switch_to` 时：

- 先确认题目环境的内核版本、架构、配置、QEMU 启动镜像和 `vmlinux` 是否匹配。前几周 MenuOS 实验采用 Linux 3.18.6、x86 32 位；若实验八仍使用该环境，以该源码树为准，不把新版本的函数名、宏或返回路径直接套用。把参考书第八章的调度和切换代码与第九章的一般执行过程分开使用。
- 在源码根目录统计直接调用和封装调用，至少分别搜索 `schedule()` 与 `schedule_timeout()`、`io_schedule()`、`cond_resched()`、`preempt_schedule()`、`preempt_schedule_irq()`、`schedule_preempt_disabled()` 等。可使用 `git grep -nE '\bschedule[[:space:]]*\(' -- '*.c' '*.h'`，再用对应表达式搜索封装调用；没有 Git 工作树时用 `rg -n --glob '*.{c,h}' '\bschedule[[:space:]]*\(' kernel arch mm fs drivers include`。逐项阅读命中上下文，剔除注释、声明和定义，并按调用者、条件、执行上下文和后续路径制作表格；搜索命中数不能直接当作调度次数或进程切换次数。
- 将“调度时机”和“发生任务切换”分开判断。检查阻塞/等待路径何时主动调用 `schedule()`，定时器或唤醒路径何时设置 `need_resched`，以及系统调用/异常/中断返回或可抢占内核路径何时检查该标志。结合本版本的 `entry_32.S`、调度器入口和 `CONFIG_PREEMPT` 配置判断实际路径。中断可能促使内核稍后调度，但不是每次中断或系统调用都切换任务；唤醒任务也不必然立即进入 `schedule()`。
- 从 `schedule()` 追到 `__schedule()`、`pick_next_task()`、`context_switch()`，再核对本架构的 `switch_to`、`__switch_to()` 和 `finish_task_switch()`。在 Linux 3.18.x x86-32 中，`context_switch()` 还可能调用 `switch_mm()` 更换用户地址空间；进程切换不是仅由一条汇编宏完成。只有源码走入 `prev != next` 分支才执行实际任务上下文切换；调度器可能选回当前任务。
- 仔细按实际的 `arch/x86/include/asm/switch_to.h` 和 `arch/x86/kernel/process_32.c` 解释汇编。Linux 3.18.6 x86-32 的宏通过保存 EFLAGS/EBP、保存 `prev->thread.sp` 和恢复 `next->thread.sp`、保存旧执行点到 `prev->thread.ip`、把 `next->thread.ip` 放到新栈并跳转 `__switch_to` 等步骤衔接两个内核执行现场；`__switch_to()` 还处理每任务的体系结构状态。逐条解释前先核对本次源码及反汇编，不能把该版本的宏当成所有架构/版本通用实现。
- 解释任务切换时，应关注切换前后的 `prev`/`next` PID、任务状态、`thread.sp`、`thread.ip` 与 `__switch_to()` 参数，并说明这些值是在断点执行前还是执行后读取。`switch_to` 是内核任务上下文切换的一部分；中断/系统调用入口建立的 `pt_regs`/返回帧属于异常或中断现场。中断返回路径可在安全位置调用调度器，而被切出的任务会保留自己的内核栈和未完成调用路径，之后恢复时从该任务自己的继续点运行。
- GDB 主路径不依赖 MenuOS 自定义命令：在匹配的 `vmlinux`/`bzImage` 上启动 `-s -S`，在内核运行前设置 `schedule()` 与 `__switch_to()` 断点，观察启动过程中首个调度调用，再继续到实际 `__switch_to()` 并核对 `prev_p`、`next_p`。启动调度可用于证明当前内核中真实发生的任务切换；若需要证明用户进程之间的具体切换，再依据当前环境选择已有命令，或检查源码/Makefile 后在本实验内构建测试。`context_switch()` 是内联函数时，断点可能不可用，应以源码和 `disassemble /m __schedule` 等方式补足。单步经过栈切换后，CPU 已在另一个任务的内核栈上，调用栈改变或源码行跳转是预期现象；不要把切换前后的帧误当成同一条普通 C 调用链。
- 断点解析后检查 `info breakpoints`：`break schedule` 可能映射到多个调用位置或内联位置，第一次停在 `schedule_preempt_disabled()` 等调用点时，结合 `bt`、`list` 说明实际入口，不要把断点名直接当作当前栈帧函数。真正停在 `__switch_to(prev_p, next_p)` 后，以不同任务指针/PID确认发生切换；任务栈切换边界的 `bt` 警告可能是调试器无法跨上下文展开。若 `comm` 或优化字段读数异常，保留异常并用可靠字段佐证，不要猜填。
- `disassemble /m __schedule` 输出过长时，用 GDB batch 模式把完整输出重定向到文本文件，再筛选 `__switch_to` 周围的指令作为截图；源码中的 `switch_to` 宏截图与反汇编短片段互补。汇编偏移、指令地址仅属于本次构建，不能泛化到其他内核/架构。
- 每轮实验都先在当前 MenuOS 执行 `help`，把结果作为本轮证据；缺少旧实验添加的 `fork` 时继续主路径，不要因此停工或立即重编译。若确需 MenuOS 测试，先确认真实启动的 `init` 来自哪份源码、Makefile 的构建和打包目标，并避免构建目标额外启动普通 QEMU。
- 分别留存源码调用点分类、`schedule()` 命中及其调用者、一次 `prev != next` 的上下文切换、`switch_to` 汇编和切换前后任务状态/栈信息。源码搜索证明有哪些潜在调用点，GDB 证明本次运行命中了哪些路径，MenuOS 输出证明用户可见的执行交替；三类证据不能互相替代。若 GDB 无法跨中断汇编展开栈，明确标注边界并用同版本源码解释，不声称完整动态跟踪。
- 博客结论需回答：哪些事件直接调用调度器、哪些事件只设置重调度标志、调度器怎样选择 `next`、何时确实执行 `switch_to`，以及任务切换与中断现场保存/恢复如何配合。总结 Linux 一般执行过程时，结合用户态执行、系统调用/中断进入内核、内核服务、可选调度、恢复原任务或切换后任务现场及返回用户态；同时说明内核线程主动调度、新 fork 子进程首次运行和 `execve` 改写返回现场等例外。

实验八的具体调用位置、GDB 断点命中、任务切换数据和截图均须以当前实验环境为准；预研结论和本次动态观察须分开记录在[课程实验学习与演进记录](references/课程实验学习与演进记录.md)中。

## 已形成的可复用基线

- **实验一：**把 C 源码、编译生成的汇编、函数调用与栈状态联系起来；区分静态推导和调试器中的动态观察。
- **实验二：**按版本和路径完成补丁、编译和 QEMU 运行；将 `mykernel` 源码与 `printk` 输出对应，并区分中断回调运行和实际调度切换。
- **实验三：**用匹配的 `vmlinux` 与 `bzImage` 通过 GDB 关键断点追踪启动；结合 `rest_init` 和 init 执行路径分析 idle 与 PID 1。

- **实验四：**通过 libc API 与 C 内嵌汇编调用同一系统调用；结合 ELF 位数、运行输出和反汇编核对调用号、参数寄存器、入口指令与返回值，并区分 libc 的错误封装和直接系统调用返回语义。
- **实验五：**以 GDB 断点观察 32 位 write 内核处理函数；用调用栈鉴别 initramfs 内核内部调用与用户态系统调用，结合 entry_32.S 分析 system_call、退出工作、条件调度和 iret。
- **实验六：**以 MenuOS fork 输出和 GDB 断点追踪 sys_clone 到 ret_from_fork；结合 copy_process/copy_thread 的源码顺序解释 task_struct、子栈和寄存器现场，并区分字段初始化前后的观测。
- **实验七：**核对 ELF 的 e_entry、PT_INTERP 和动态依赖；结合 execv/MenuOS 运行及 sys_execve → load_elf_binary → start_thread 断点解释静态程序直接进入应用入口、动态程序先进入解释器，以及初始用户栈的证据边界。
