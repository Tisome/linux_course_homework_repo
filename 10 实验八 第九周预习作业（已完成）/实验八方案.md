# 实验八方案：进程调度时机与上下文切换

**状态：**预研方案；云端路径、镜像文件和 MenuOS 命令已初步核验，GDB 切换过程尚未实测  
**默认实验环境：**暂按前几周已用的 Linux 3.18.6、x86 32 位、QEMU、GDB、MenuOS 规划，启动前须核实。  
**目标：**梳理 `schedule()` 调用点，实测一次实际任务切换，细读 x86 32 位 `switch_to`，解释它与中断现场保存/恢复的关系。

## 一、依据前几周结果修正本次重点

- **实验二（mykernel）：**定时器处理函数有日志只能证明回调运行，不能证明调度器选择了另一任务。因此本次必须出现可核对的 `prev != next` 或等效切换证据。
- **实验五（system_call）：**Linux 3.18.6 的 `entry_32.S` 返回路径在 `work_pending` 检查 `need_resched` 后才调用 `schedule()`。这说明系统调用退出前存在条件性调度点，并非每次系统调用都切换。此前 GDB 无法跨汇编入口完整回溯，故本次预留源码与动态证据分层说明。
- **实验六（fork）：**已有 MenuOS `fork` 测试和 `ret_from_fork` 断点经验，可用来解释新任务第一次运行时的特殊起点；但上一实验只证明父子创建和首次入口，没有专门验证一般的调度选择和切换。
- **实验七（execve）：**新程序入口由内核准备，不能和普通任务切换混为一谈。总结一般执行过程时，应把 `execve` 改写返回现场作为特殊路径。

## 四、源码搜索：列出调度调用点并验证课程总结

在内核源码根目录分别搜索直接调用和常见封装：

```bash
git grep -nE '\bschedule[[:space:]]*\(' -- '*.c' '*.h'
git grep -nE '\b(schedule_timeout|io_schedule|cond_resched|preempt_schedule|preempt_schedule_irq|schedule_preempt_disabled)[[:space:]]*\(' -- '*.c' '*.h'
```

若源码树不是 Git 工作树，可用：

```bash
rg -n --glob '*.{c,h}' '\bschedule[[:space:]]*\(' kernel arch mm fs drivers include
```

搜索输出先作为候选清单。逐个阅读上下文，区别实际调用、函数定义、声明、注释、封装和条件分支。最终整理成表格：

| 记录项 | 要确认的内容 |
|---|---|
| 文件、函数、源码位置 | 本次源码里实际命中的位置 |
| 触发条件 | 主动等待/睡眠、任务状态变化、重调度标记或显式调用 |
| 运行上下文 | 普通任务内核态、系统调用/异常返回路径、IRQ 返回路径、内核线程等 |
| 调度路径 | 直接 `schedule()`，还是经封装/抢占入口进入调度器 |
| 是否实际切换 | 调度器的 `prev` 和 `next` 是否不同；源码搜索本身不能回答 |

优先逐层核对：

1. `kernel/sched/core.c` 中 `schedule()`、`__schedule()`、`pick_next_task()`、`context_switch()` 和 `finish_task_switch()`；并查看该版本的定时器 tick、唤醒及 `need_resched` 设置路径。
2. `arch/x86/kernel/entry_32.S` 的系统调用返回 `work_pending` 以及中断/异常返回到可抢占上下文的路径。
3. `arch/x86/include/asm/switch_to.h` 的 x86-32 `switch_to` 宏和 `arch/x86/kernel/process_32.c` 的 `__switch_to()`。
4. 搜索发现的等待、休眠、内核线程等其他代表性调用者。

**待验证的判断，不作为预先写定的实验结果：**阻塞任务可以主动进入调度；定时器或唤醒可能设置 `need_resched`，实际调度会在适当的内核/返回路径发生；`schedule()` 是调度入口，但只有选择不同任务时才发生任务上下文切换；中断本身不等于任务切换。以本次源码、配置和 GDB 命中路径判断这些说法是否准确。

## 五、选择能观察到真实切换的测试场景

**主路径：观察 Linux 启动时本来就会发生的调度切换。**内核启动期间会创建并运行 init、kthreadd 等任务，调度器会在它们之间切换；这条路径不依赖 MenuOS 自定义命令。用 `schedule()` 断点看调度入口，再用 `__switch_to()` 参数确认 `prev`/`next`，是当前重置环境下最小、最直接的实验。

**可选扩展：观察用户任务切换。**只有题目分析需要用户进程级的父子/阻塞场景时，才在当前实验环境检查 MenuOS 源码和 Makefile，构造本轮测试并重新编译、打包实际启动的 `init`。构建步骤必须按云机中的真实文件确认；不要假设旧命令仍在，也不要盲目调用会额外启动普通 QEMU 的总目标。

无论采用哪条路径，`schedule()` 命中、`need_resched` 日志或用户输出本身都不等同于任务切换。动态切换证据以 `__switch_to()` 中不同任务的参数为准；如字段读数异常，同时检查 `prev_p` 和 `next_p` 指针地址、断点所在源码位置及当前调试符号。

## 六、GDB 执行步骤与断点策略

### 1. 在内核启动前设置断点

本轮 MenuOS 没有 `fork`，因此不设置 `sys_clone` 锚点，也不在此处修改/重编译 MenuOS。使用本轮已确认匹配的 `vmlinux`、`bzImage` 启动 `-s -S`，在内核继续运行前设置两个断点：

```gdb
(gdb) set pagination off
(gdb) target remote :1234
(gdb) break schedule
(gdb) break __switch_to
(gdb) info breakpoints
(gdb) continue
```

`break schedule` 可能解析到多个调用点/内联位置。本轮 GDB 已解析到 5 个位置，首次命中的是 `schedule_preempt_disabled()` 中调用 `schedule()` 的位置（`kernel/sched/core.c:2901`），并非 
**每次都会停在同一个函数入口。**用 `info breakpoints`、`bt` 和 `list` 判明实际停点。若某个符号无法设置断点，再用 `info functions schedule` 或 `info functions __switch_to` 核实本次符号，不要跳过错误后声称命中。

### 2. 在 `schedule()` 识别为什么开始调度

```gdb
(gdb) bt
(gdb) list
(gdb) info args
(gdb) info breakpoints
```

保存 `schedule()` 入口的调用栈和源码位置。启动期调用者可能与 MenuOS 用户命令无关；按实际调用栈说明它来自哪个启动/内核线程路径，不要硬写成系统调用返回路径。查看 `info breakpoints` 的编号，禁用 `schedule` 对应断点，然后继续运行，使 GDB 停到仍启用的 `__switch_to()` 断点：

```gdb
(gdb) disable <schedule断点编号>
(gdb) continue
```

### 3. 在 `__switch_to()` 验证实际切换

```gdb
(gdb) break __switch_to
(gdb) continue
(gdb) info args
(gdb) p prev_p->pid
(gdb) p next_p->pid
(gdb) p prev_p->comm
(gdb) p next_p->comm
(gdb) p/x prev_p->thread.sp
(gdb) p/x next_p->thread.sp
(gdb) bt
```

如果该构建下参数名、调试信息或符号表现不同，按 `list`、`info functions` 和 `disassemble /m __schedule` 选择可用观察点。`context_switch()` 在该版本为内联代码，断点不可用时不要将其误判为路径没有执行。记录两个任务的 PID、名称、可读取的栈字段和停留源码位置；若 GDB 在 `__switch_to()` 多次停下，逐次继续并保留第一次能完整读取参数的实际切换。切换点处 `%esp` 和栈帧会从一个任务转到另一个任务，普通连续 C 回溯不一定成立。

### 4. 把源码与反汇编逐步对应

Linux 3.18.6 x86-32 的 `switch_to` 宏应逐项对照本机源码。本书所示关键序列包括：压入并保存 EFLAGS、保存 EBP、把当前 ESP 保存到 `prev->thread.sp`、装载 `next->thread.sp`、把局部标签地址保存为 `prev->thread.ip`、把 `next->thread.ip` 压入新栈并跳转 `__switch_to`；返回到某个任务的本地标签后，恢复该任务的 EBP 和标志寄存器。`__switch_to()` 还负责每任务体系结构状态的切换/更新。

`disassemble /m __schedule` 的完整输出可能很长，不要求整屏截图。把完整反汇编保存为文本证据，再只截取 `switch_to`/`__switch_to` 附近的短片段；汇编宏的主证据仍是本轮 `switch_to.h` 源码截图，不能将超长输出的局部截图说成整个函数。

现场讲解时确认寄存器的断点前后状态：

- 切换前：当前任务内核栈、将被保存的继续点、调度器选出的 `next`。
- 汇编切换处：ESP 如何从旧任务内核栈转到新任务内核栈，EIP/继续位置如何配套。
- 切换后：进入新任务的既有内核继续点；新 fork 任务可能进入 `ret_from_fork`，这与已运行过的任务恢复局部标签不同。
- 若采集不到某字段的动态值，引用源码的赋值/恢复关系并标为源码分析，绝不以函数入口的旧值冒充最终状态。

`context_switch()` 的 `switch_mm()` 和 `switch_to()` 作用要分开说明：前者按需要处理地址空间，后者衔接 CPU 寄存器/内核栈执行现场。共享地址空间的线程可能不需要像不同 `mm` 进程那样切换页表。

## 七、进程切换与中断上下文的关系

用两层状态来讲清楚：

1. **中断/系统调用现场：**CPU 和入口汇编建立返回现场并保存相应寄存器，Linux 入口/退出汇编通过 `pt_regs`、`SAVE_ALL` 或该版本对应机制处理现场。用户态任务进入内核后，内核仍在该任务的执行上下文中运行。
2. **任务上下文切换：**调度器选出另一个任务后，内核切换每个任务的内核栈和体系结构执行状态；被切出的任务保留尚未完成的内核调用/中断返回路径，之后重新获得 CPU 时从自己的继续点恢复。

中断可设置重调度标志，之后在适当的返回/抢占点进入调度；中断入口压栈与 `switch_to` 的任务切栈不是同一件事。硬中断处理上下文不能像普通进程上下文那样阻塞睡眠。实际描述应检查本版本 `entry_32.S`、配置和 GDB 调用栈，避免简化成“每次中断结束都切换进程”。
