## 0. 准备

在云端 Linux 桌面打开两个终端：终端 A 用来启动 QEMU，终端 B 用来搜源码和运行 GDB。先在任一终端输入：

~~~bash
mkdir -p ~/Desktop/exp8-screens
cd ~/LinuxKernel
pwd
ls -l linux-3.18.6/vmlinux linux-3.18.6/arch/x86/boot/bzImage rootfs.img
file linux-3.18.6/vmlinux linux-3.18.6/arch/x86/boot/bzImage
~~~

三个文件都显示出来再继续。截图按文件名 **01-环境和内核镜像.png** 保存到本机图片目录。

cd ~/LinuxKernel

## 2. 搜索 schedule() 调用位置

终端 B 输入：

~~~bash
cd ~/LinuxKernel/linux-3.18.6
grep -RInE '(^|[^[:alnum:]_])schedule[[:space:]]*\(' --include='*.c' --include='*.h' kernel arch mm fs drivers include > ~/Desktop/exp8-screens/schedule-callers.txt
grep -RInE '(schedule_timeout|io_schedule|cond_resched|preempt_schedule|preempt_schedule_irq|schedule_preempt_disabled)[[:space:]]*\(' --include='*.c' --include='*.h' kernel arch mm fs drivers include > ~/Desktop/exp8-screens/schedule-wrappers.txt
wc -l ~/Desktop/exp8-screens/schedule-callers.txt ~/Desktop/exp8-screens/schedule-wrappers.txt
head -n 35 ~/Desktop/exp8-screens/schedule-callers.txt
~~~

搜索结果完整保存在两个 txt 文件里。截图 wc 和 head 输出为 03-schedule调用点搜索上半.png；前 35 行只是预览，不是全部调用位置。要分清真正调用、定义、声明和注释。

继续查看本次要讲的源码：

~~~bash
grep -n -A28 -E 'asmlinkage __visible void __sched schedule' kernel/sched/core.c
grep -n -A50 -E 'context_switch\(struct rq' kernel/sched/core.c
grep -n -A48 -E '^#define switch_to\(prev, next, last\)' arch/x86/include/asm/switch_to.h
grep -n -A32 '^work_pending:' arch/x86/kernel/entry_32.S
~~~

分别截屏保存：
- 05-schedule函数源码.png：显示 `schedule()` 函数主体。
- 06-context_switch与switch_to调用.png：包含 `context_switch()`、`switch_mm()` 和 `switch_to()` 调用。
- 07-switch_to宏源码主体.png：看清保存旧 ESP/EIP、载入新 ESP/EIP、跳转 `__switch_to` 和恢复现场。
- 08-switch_to宏续页与架构分支.png：接续展示宏约束和架构分支。
- 09-work_pending条件调度源码.png：看清 `TIF_NEED_RESCHED` 检查和 `call schedule`。

## 3. 用 GDB 跟踪

终端 A 启动调试 QEMU：

~~~bash
cd ~/LinuxKernel
qemu -kernel linux-3.18.6/arch/x86/boot/bzImage -initrd rootfs.img -s -S
~~~

QEMU 占住终端 A 后，切到终端 B：

~~~bash
cd ~/LinuxKernel
gdb linux-3.18.6/vmlinux
~~~

在 GDB 提示符逐行输入：

~~~gdb
set pagination off
target remote :1234
break schedule
break __switch_to
info breakpoints
continue
~~~

`break schedule` 可能解析成多个位置。你这次的 GDB 确实列出了 5 个位置，继续后先停在 `schedule_preempt_disabled()` 中调用 `schedule()` 的位置（`kernel/sched/core.c:2901`）。在 GDB 输入下面几条命令，结合 `bt` 和 `list` 识别真实调用路径：

~~~gdb
bt
list
info args
~~~

截图保存为 **10-GDB启动期schedule断点.png**。画面要有 `schedule()` 位置和调用栈；启动期调用者不一定是 MenuOS 命令，要按实际 `bt` 解释。

再输入：

~~~gdb
info breakpoints
~~~

通常断点 1 是 `schedule`、断点 2 是 `__switch_to`。按这次 `info breakpoints` 实际显示的编号，禁用 `schedule` 对应断点；例如：

~~~gdb
disable 1
continue
~~~

GDB 会继续运行并在实际执行 `__switch_to()` 时停下。此时逐行输入：

~~~gdb
info args
p prev_p->pid
p next_p->pid
p prev_p->comm
p next_p->comm
p/x prev_p->thread.sp
p/x next_p->thread.sp
bt
~~~

截图保存为 **11-GDB实际切换-PID0到PID2.png**。记录两个 PID、任务名和可读的栈地址。`__switch_to()` 的参数就是实际切换双方；若 PID 或字段显示异常，再输入 `p prev_p`、`p next_p` 查看指针，并把异常一并截下，不要自己补数字。

如果 `schedule()` 命中后没有马上停到 `__switch_to()`，可能这次调度选回当前任务；保持 `__switch_to` 断点启用并继续运行，直到它命中。只有停在 `__switch_to()` 并读到两个任务参数，才把它记录为本次真实切换。

## 4. 截取反汇编

`disassemble /m __schedule` 会输出很长，不要试图把整个输出截进一张图。保留当前远程 GDB 会话不动，另开一个终端 C，把完整反汇编直接保存成文本：

~~~bash
cd ~/LinuxKernel
gdb -batch -ex 'set pagination off' -ex 'file linux-3.18.6/vmlinux' -ex 'disassemble /m __schedule' -ex 'disassemble /m __switch_to' > ~/Desktop/exp8-screens/exp8-disassembly.txt 2>&1
~~~

然后只显示 `__switch_to` 附近的片段：

~~~bash
grep -n -B 12 -A 12 -m 1 '__switch_to' ~/Desktop/exp8-screens/exp8-disassembly.txt
~~~

把这段短输出截为 **12-GDB-switch_to反汇编.png**，同时保留完整的 `exp8-disassembly.txt`。不要截取整段超长反汇编；若关键汇编只在源码宏中可见，就以第 3 节的 `switch_to.h` 截图作为主证据。若 `grep` 没找到 `__switch_to` 或没有显示宏展开，不要反复截长输出；`switch_to` 的汇编宏以第 2 步的源码截图为主，并在分析中说明动态反汇编未能展示宏展开。
